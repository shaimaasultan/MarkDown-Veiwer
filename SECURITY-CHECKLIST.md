# Security checklist — Markdown Viewer (WebView2)

Every hardening point added to this app, where it lives and how it was checked. `[x]` = done and tested;
`[ ]` = done, but still to be confirmed on a real run (these steps need a Windows administrator or signing
prompt, which the automated tests cannot click). Version numbers show when each point was added.
`[ ] To do:` = not done yet. (The points found by comparing with the CloClo widget were all done in 1.8.6–1.8.8; none are open.)

**How to re-check:** `app\Setup Scripts\cmd\Check-Source.cmd` (project files unchanged since the last install) and the
tamper tests described under each section.

---

## 2. Private viewer, no update check of its own

- [x] No network port: the page lives at a private in-app address; every request is answered by the program
- [x] All libraries bundled; the WebView2 engine cannot resolve any internet name; no document content is sent online
- [x] **The viewer never goes online, not even for updates** (2026-10-25 review): the daily in-app WebView2 SDK check (a signed PowerShell helper in the Content DLL, contacting `api.nuget.org`) is removed - its endpoint, the helper and its resource are gone. It never worked on a real install: `powershell.exe` is catalog-signed and the viewer's signature check reads embedded signatures only, so the header always said "Check unavailable". It was also the viewer's only network path, for a result users cannot act on. The header tag now shows the WebView2 Runtime version
- [x] **Note - how WebView2 is updated:** the **Runtime** (the engine, nearly all security fixes) is updated by Windows automatically and used at the next start; the **SDK** (the three DLLs next to the program) stays bundled and pinned by SHA-256 and changes only with a new signed build. The SDK DLLs cannot be removed or taken from elsewhere: Windows does not provide them, and the pinned hashes are what keep any other copy from loading (README › How WebView2 is kept up to date)
- [x] **SDK update reminder:** `Check-Updates.cmd` records a newer SDK on a line of its own; `Install.cmd` then shows a yellow "REMINDER - WebView2 SDK update" at every install until the DLLs in `app\Setup Scripts\webview2\` reach that version — tested: with 1.0.4314.35 found and 1.0.4258.31 in the project, the reminder shows and the SDK is not listed twice
- [x] **Engine vs app SDK on every PC:** Windows provides no WebView2 SDK (checked: nothing in System32 / SysWOW64 or the Runtime folder; other apps each bundle their own, six versions on the build PC), so the dialog compares the engine's build with the app's SDK build: engine older → Windows Update; SDK about 3 engine releases (~180 builds) or more behind → ask for a newer app version. It also always shows what it read from the Check-Updates record — tested in the page with an up-to-date and a far-ahead engine
- [x] **The WebView2 tag explains updates without going online:** a click opens *WebView2 on this PC*, built from `<token>/webview2` (gated like the other program addresses): the Runtime version and when Windows installed it (the creation time of the checked engine's version folder), the SDK version, the app's build time (the program's PE link time; a deterministic hash is never shown as a date) and, on the PC that builds the app, the last `Check-Updates.cmd` result. Advice: engine older than 45 days → Windows Update / Microsoft's Runtime download (the link goes through the usual question); engine build older than the SDK build → update the engine; build older than 120 days → look for a newer app version; newer SDK found by `Check-Updates.cmd` → the update steps. Values are put in with `textContent` — tested: the program's answer on this PC (Runtime 155.0.4283.62 installed 2026-10-19, SDK 1.0.4258.31, newer SDK 1.0.4314.35 found) and a stale-engine / old-build case, light and dark
  - [ ] Confirm on a real run: after `Install.cmd`, the header tag reads `WebView2 <Runtime version>` with the Runtime and SDK in its tooltip; the old `webview2-update-status.txt` is gone after the next `Check-Updates.cmd`
- [x] Web and mail links open outside only after a question showing the real address (1.5.0)
- [x] Only `http:`, `https:` and `mailto:` addresses are ever handed to Windows; any other scheme is ignored (`AskOpenOutside`)
- [x] **Mail links show every recipient:** the question lists To, Cc and Bcc in full, the subject and the start of the text, so a long text can no longer push a `bcc=` out of view. A mail link with any other part (`attach=`, `attachment=`, headers) is not opened, as some mail apps attach the named file (`DescribeMailLink`) — tested on the compiled code: long text + Bcc shown, `attach` / `ATTACHMENT` and unknown parts refused
  - [ ] Confirm on a real run: click a `mailto:` link with Cc / Bcc → the question lists them; one with `attach=` → "not opened"
- [x] Settings saved through a temporary file and an atomic replace, so a crash while saving cannot corrupt `settings.ini` and silently reset choices such as Pictures off (1.8.6) — tested: saved value present, no temporary file left
- [x] The temporary settings file gets a random name and is created with `CreateNew`, so nothing can place a file or link there beforehand to redirect the write (1.8.8) — tested: two saves, no temporary file left
- [x] InPrivate window; camera, microphone, location, notifications, clipboard reading refused; downloads only from the viewer; trimmed right-click menu (1.5.0)
- [ ] **Frames, other programs' schemes and screen capture refused:** a frame may only hold content the page writes in (`about:srcdoc`, the HTML preview); a link can never start another program through its scheme (`ms-settings:`, `search-ms:` …; web and mail links still go through the question); screen, window and tab capture is cancelled (`FrameNavigationStarting`, `LaunchingExternalUriScheme`, `ScreenCaptureStarting`) — added in the 2026-10-25 review as defence in depth (nothing found that reached them); compiled, still to be confirmed on a real run: an HTML file's Preview still shows, web and mail links still ask

## Known limits (by design)

- Windows' administrator prompt is not a security boundary against programs already running as you: they
  could change this repository's scripts or sources before you install. Use `Check-Source.cmd` and
  `git status` before installing, and confirm a signing request only while a build you started is running.
- `app\dist\` is for testing only; full protection applies to the installed copy in Program Files.
- Setup, like any program started from the Downloads folder, cannot stop Windows from loading a few system
  DLLs from its own folder before its first line runs; this affects only the non-elevated window (the
  administrator step never starts Setup). On another PC Windows shows the publisher as unknown unless the
  certificate is trusted there, and Setup installs no project record of its own (`Check-Source.cmd` is for the PC that builds; an existing record is kept).
- Viewer firewall rules cover `MarkdownViewerWebView2.exe`, not the shared WebView2 engine. The separate Python firewall tool affects all applications using the exact trusted `python.exe` and `py.exe` paths found on its PATH; its rules persist after viewer uninstall until removed by choosing Remove in `Python-Firewall.cmd`.
- Signatures carry no timestamp (builds never go online). The signing certificate is valid until October
  2036; after that the start-up check refuses the program, so install a build signed with a new
  certificate before then.
- One viewer at a time is per program file: a test build in `app\dist` and the installed copy are different files, so each runs as its own viewer.
- The library update checks each package against the SHA-512 published by the same registry: it catches a damaged or swapped download, not a release published through a compromised npm account. The 7-day hold and the viewer test reduce that risk; still check the changes (`git diff --stat app/source`) before installing.
- The update check trusts what nuget.org and the npm registry report as the latest version; it only reports, and every update is still checked (Microsoft signature, pinned hashes, the build's version checks) before it is built.
- Not applicable from the CloClo comparison (this app has no such feature): weather and network requests,
  clipboard and selection reading, screen-capture exclusion, dictation, colour picker, HTTP limits,
  notification logos, `.pfx` signing.
